# گزارش بازنشدن بعضی سایت‌ها در مرورگر

گزارش کاربر: YouTube در Firefox/Chrome باز نمی‌شود، ولی سایت بررسی IP و Telegram قابل استفاده‌اند. لاگ جدید همین آزمایش یا دسترسی به ویندوز کاربر در اختیار نیست؛ نتیجهٔ زیر بررسی کد و کانفیگ است، نه اثبات علت نهایی روی شبکهٔ کاربر.

## یافته‌ها و اصلاح

| یافتهٔ قطعی در کد قبلی | اثر محتمل | اصلاح |
| --- | --- | --- |
| پیش‌فرض ExcludeSelectedApps بود. | مرورگر انتخاب‌شده مستقیم می‌رفت و سایت مسدودشده باز نمی‌شد. | انتخاب حالت حذف شد؛ برنامهٔ انتخاب‌شده وارد سیاست VPN می‌شود. |
| قانون DNS برنامه‌های انتخاب‌نشده شامل svchost.exe هم می‌شد. | DNS مشترک ویندوز می‌توانست از مسیر مستقیم پاسخ بگیرد، حتی وقتی مرورگر داخل VPN بود. | DNS سرویس مشترک پیش از قانون مستقیم، به dns-remote می‌رود؛ ترافیک عادی svchost مستقیم می‌ماند. |
| reject مربوط به UDP/443 بعد از sniff بود و no_drop نداشت. | بستهٔ QUIC می‌توانست بدون پاسخ سریع رها شود و مرورگر در تلاش HTTP/3 معطل بماند. | همان سیاست رد QUIC، پیش از sniff، فقط برای TUN و با no_drop=true اعمال می‌شود؛ استثناهای هسته مقدم‌اند. |
| قانون DNS پردازش قبل از پاسخ‌های predefined قرار می‌گرفت. | حتی localhost ممکن بود به resolver بیرونی برسد. | پاسخ‌های predefined اولویت دارند. |

هیچ قانون ویژه‌ای برای اجبار YouTube از مرورگر انتخاب‌نشده به VPN اضافه نشده است. نام‌های youtube.com، googlevideo.com و ytimg.com فقط در تست‌ها هستند؛ مسیر واقعی تابع انتخاب برنامه است. سایت بررسی IP که صرفاً باز می‌شود، به‌تنهایی عبور از VPN را اثبات نمی‌کند؛ مقدار IP نمایش‌داده‌شده هم باید مقایسه شود.

## رفتار جدید

- گزینهٔ داخل/خارج حذف شده است. انتخاب‌شده‌ها داخل VPN و برنامه‌های شناسایی‌شدهٔ انتخاب‌نشده مستقیم‌اند.
- فهرست و Enabled قبلی حفظ می‌شود؛ Mode قبلی کنار گذاشته می‌شود. ذخیرهٔ جدید schema نسخهٔ ۲ است. نسخهٔ قدیمی اپ که فقط schema ۱ را می‌شناسد، برای بازگشت نیاز به تنظیم مجدد split خواهد داشت.
- DNS مشترک ویندوز استثناست و داخل VPN می‌رود. موتور فقط صاحب سوکت DNS را می‌بیند و همیشه مرورگر درخواست‌کننده را نمی‌شناسد.
- ترافیک بدون هویت پردازش و ترافیک اشتراک‌گذاری روی سیاست قبلی VPN باقی می‌مانند؛ این پیاده‌سازی برای اتصال فاقد هویت، تضمین تفکیک برنامه ارائه نمی‌کند. برنامه‌های child/helper با مسیر متفاوت باید جداگانه یا با پوشه انتخاب شوند.
- Geo/AI/شیلد موجود برای برنامه‌های داخل VPN برقرارند. نبود فایل Geo همچنان اتصال را متوقف نمی‌کند.

## اعتبارسنجی انجام‌شده

۶۴ بررسی شامل بازتولید رد QUIC پس از sniff در کانفیگ قبلی، رد سریع در کانفیگ جدید، استثنای هسته، DNS مرورگر و svchost برای دامنه‌های YouTube/CDN/IP، DNS مستقیم برنامهٔ انتخاب‌نشده، localhost، ورودی mixed، مهاجرت هر دو حالت قدیمی و حفظ انتخاب‌ها گذشت.

کانفیگ‌های `SelectedOnly.json` و `NormalTun.json` با فرمان `sing-box 1.14.0 check` پذیرفته شدند. fixture خروجی‌های SOCKS محلی و direct دارد و outbound قدیمی block هستهٔ سفارشی را برای schema رسمی جایگزین می‌کند. این آزمون اتصال زنده ایجاد نکرده است. صفحات WPF تغییرکرده در harness مستقل C# 7.3 کامپایل شدند؛ بیلد کامل net48/Costura و اجرای واقعی ویندوز هنوز لازم است.

## تست روی ویندوز

1. خروجی جدید را بسازید؛ مرورگرها را کامل ببندید و VPN را قطع کنید.
2. برای حذف پاسخ DNS قبلی، یک بار `ipconfig /flushdns` اجرا کنید. این تغییر DNS سرور یا غیرفعال‌کردن IPv6 نیست.
3. تقسیم تونل را روشن کنید، فقط Chrome را انتخاب و ذخیره کنید، سپس وصل شوید.
4. Chrome و Firefox را تازه باز کنید. IP هر دو را بررسی کنید؛ Chrome باید مسیر VPN و Firefox مسیر مستقیم داشته باشد. در Chrome صفحهٔ YouTube و پخش ویدئو را جداگانه بررسی کنید.
5. اتصال را قطع کنید، انتخاب را با Firefox عوض کنید و تست را تکرار کنید. Telegram انتخاب‌شده، مرورگر انتخاب‌نشده و اشتراک‌گذاری را هم بررسی کنید.
6. اگر YouTube همچنان مشکل داشت، زمان آزمایش، سرور/پروتکل، وضعیت split و خطای دقیق مرورگر همراه لاگ تازه لازم است؛ در آن مرحله خروجی سرور، IPv6، DNS و HTTP/3 باید جداگانه مقایسه شوند.
