# تقسیم تونل برنامه‌ها در IRSPEEDY

مرجع: Moonlight Tunneling، کامیت `526893732c2f38f86c792e32455349b5aa075d66`.
فایل‌های ShellLinks و ConnectionTables و منطق محدود تطبیق مسیر از مرجع MIT اقتباس شده‌اند؛ مجوز در `docs/third-party` و داخل اسمبلی خروجی قرار می‌گیرد. پروژه با .NET Framework 4.8 و بسته‌بندی فعلی Costura باقی می‌ماند. درایور، سرویس ویندوز، فایروال یا هستهٔ دوم اضافه نمی‌شود.

## استفاده

قبل از اتصال: تنظیمات سرویس ← روش‌های اتصال ← حالت TUN ← تقسیم تونل.
**فقط برنامه‌های انتخاب‌شده داخل VPN هستند.** انتخاب حالت حذف شده است. سایر برنامه‌هایی که صاحب اتصالشان شناسایی شده است مستقیم متصل می‌شوند. فهرست خالی یعنی هیچ برنامهٔ شناسایی‌شده‌ای از VPN استفاده نمی‌کند. استثناهای ترافیک مشترک در بخش مرزها توضیح داده شده‌اند.

فهرست را ذخیره کنید و کلید تقسیم تونل را در روش‌های اتصال روشن و ذخیره کنید. انتخاب‌ها در اتصال بعدی و اتصال مجدد اعمال می‌شوند. برنامه‌ها یا اتصال‌های باز آن‌ها به‌زور بسته نمی‌شوند. برای آزمون مسیر، اتصال تازهٔ برنامه را ایجاد کنید.

تنظیمات پیش‌نمایش قدیمی به فهرست جدید وارد می‌شوند، ولی فعال‌سازی واقعی نیاز به روشن‌کردن کلید دارد. تنظیمات نسخهٔ ۱ از هر دو حالت قبلی با حفظ فهرست و وضعیت روشن/خاموش به سیاست ثابت «انتخاب‌شده داخل VPN» تبدیل می‌شوند؛ schema جدید نسخهٔ ۲ است و Mode ندارد. حالت بازی و تقسیم تونل هم‌زمان فعال نمی‌شوند؛ رابط، انتخاب جدید را مقدم می‌کند. در صورت وجود تنظیمات قدیمی متعارض، سیاست تقسیم تونل catch-all حالت بازی را اصلاح می‌کند.

## کشف و انتخاب برنامه‌ها

`AppDiscoveryService` میان‌برهای Start Menu کاربر و سیستم را با `IShellLinkW` روی thread مستقل STA می‌خواند؛ رجیستری App Paths/Uninstall در HKCU/HKLM و هر دو نمای ۳۲/۶۴ بیت و جدول‌های TCP/UDP IPv4/IPv6 را نیز بررسی می‌کند. دسترسی غیرمجاز به یک پوشه/پردازش کل فهرست را متوقف نمی‌کند. اسکن عمومی دیسک انجام نمی‌شود؛ junctionهای Start Menu دنبال نمی‌شوند.

اولویت نام/مسیر با Start Menu است؛ سپس رجیستری و پردازش شبکه. تکرار بر اساس هویت مسیر حذف می‌شود. نمایش فهرست منتظر آیکون‌ها نمی‌ماند. داده‌ها دو دقیقه در حافظه cache می‌شوند و دکمهٔ تازه‌سازی خواندن مجدد را اجبار می‌کند. جستجو فقط روی همین فهرست است.

افزودن دستی فایل `.exe` یا پوشه فراهم است. **انتخاب پوشه همهٔ فایل‌های اجرایی زیرپوشه‌ها را نیز شامل می‌شود**. پوشهٔ ویندوز، ریشهٔ درایو و ریشه‌های عمومی برنامه‌ها پذیرفته نمی‌شوند. فایل‌های حذف‌شدهٔ قبلاً انتخاب‌شده با «پیدا نشد» حفظ می‌شوند و قابل لغو انتخاب هستند.

برای برنامه‌های Squirrel مثل Discord، مسیر `root\app-*\App.exe` با الگوی محدود به همان root و نام فایل پوشش داده می‌شود؛ میان‌بر Update.exe در صورت شناسایی بدون ابهام به برنامهٔ واقعی تبدیل می‌شود. همهٔ launcherها و Store apps تضمین نمی‌شوند. WindowsApps فعلاً فقط با مسیر اجرایی دقیق قابل انتخاب است و بعد از تغییر مسیر ممکن است نیاز به انتخاب مجدد داشته باشد. مسیر خام regex از کاربر/رجیستری پذیرفته نمی‌شود.

## اتصال به هسته

`SplitTunnelStore` دادهٔ schema نسخهٔ ۲ را در کلید موجود `SplitTunnelSettingsV1` رجیستری ذخیره می‌کند؛ نام کلید برای مهاجرت همان نام قدیمی مانده است. `SplitTunnelPolicyBuilder` بعد از GeoRoutingFallback و پیش از Core.Start در `TryStartCoreWithConfig` اعمال می‌شود؛ همان نقطه برای اتصال عادی، Smart و restart/reconnect به کار می‌رود. مسیرهای برنامه در لاگ چاپ نمی‌شوند؛ فقط سیاست ثابت و تعداد انتخاب‌ها ثبت می‌شود.

قواعد برنامه با `process_path_regex` سازگار با RE2 ساخته می‌شوند. ترتیب اجرای آن‌ها:

1. استثنای پردازش‌های داخلی هسته برای جلوگیری از حلقه.
2. گرفتن DNS ورودی TUN.
3. قانون خروج مستقیم برنامه‌های شناسایی‌شدهٔ انتخاب‌نشده.
4. رد سریع UDP/443 ورودی TUN، پیش از sniff، برای برگشت مرورگر انتخاب‌شده به TCP.
5. قوانین موجود sniff، Geo، AI، شیلد و مسیر پیش‌فرض VPN.

`TunBrowserCompatibility` قانون موجود UDP/443 را قبل از sniff منتقل می‌کند و `method=default, no_drop=true` می‌گذارد. این اصلاح مستقل از فعال‌بودن split در اتصال TUN اعمال می‌شود. استثنای هسته مقدم می‌ماند؛ ورودی mixed مشمول محدودیت جدید نمی‌شود.

قانون مستقیم فقط ورودی TUN را پوشش می‌دهد و خروجی اختصاصی `split-direct` دارد؛ زنجیرهٔ پیش‌فرض نمی‌تواند آن را دوباره داخل VPN ببرد. ترافیک mixed/proxy اشتراک‌گذاری از انتخاب‌های برنامه‌ها اثر نمی‌گیرد. DNS قابل انتساب به برنامهٔ مستقیم از resolver اختصاصی با detour مستقیم استفاده می‌کند؛ cache این قانون غیرفعال است تا در هسته‌های قدیمی با cache مشترک، پاسخ مستقیم وارد cache مسیر VPN نشود. DNS برنامهٔ انتخاب‌شده و DNS بدون هویت برنامه از `dns-remote` استفاده می‌کند. **DNS سرویس مشترک ویندوز (`svchost.exe`) هم از VPN می‌رود**: این پردازش لزوماً برنامهٔ درخواست‌کننده نیست. فقط درخواست DNS استثناست؛ ترافیک عادی svchost در صورت انتخاب‌نشدن مستقیم است. پاسخ‌های predefined مثل localhost پیش از قواعد پردازش حفظ می‌شوند.

IPv6 به آدرس‌های TUN اضافه می‌شود تا از قواعد برنامه‌ها خارج نماند. این تنظیم به معنی افزودن پشتیبانی IPv6 به سروری که ندارد نیست؛ باید روی سرورهای واقعی آزموده شود.

**مرزها:** برنامه‌های داخل VPN همچنان تابع قوانین سراسری Geo/AI/شیلد هستند؛ مقصدهای مستثنای سراسری لزوماً از خروجی خارجی عبور نمی‌کنند. ترافیک ناشناس و فورواردشدهٔ هات‌اسپات بدون هویت برنامه روی سیاست VPN می‌ماند. تطبیق مسیر، وراثت خودکار برای همهٔ child processها نیست؛ برای لانچرها پوشه یا فایل‌های کمکی لازم را انتخاب کنید. پردازش مشترک WebView2 ممکن است چند اپ را با هم شامل کند. Kill switch اختصاصی جدید اضافه نشده است.

## بررسی‌های انجام‌شده و آزمون ویندوز

- `dotnet run --project tests/SplitTunnelChecks -c Release`: سیاست ثابت انتخاب برنامه، اولویت QUIC پیش از sniff، هسته، ورودی mixed، ترافیک ناشناس، DNS سرویس مشترک ویندوز، localhost، IPv6، نبود Geo، الگوهای نسخه/پوشه، اعتبارسنجی و مهاجرت هر دو حالت قدیمی.
- کانفیگ‌های نمونهٔ TUN عادی و SelectedOnly با `sing-box 1.14.0 check` بررسی می‌شوند؛ fixture از خروجی تولیدی سیاست استفاده می‌کند ولی outbound قدیمی block هستهٔ سفارشی را برای schema نسخهٔ رسمی جایگزین می‌کند. این بررسی هیچ TUN یا اتصال زنده‌ای باز نمی‌کند.
- صفحات تغییرکرده در harness مستقل WPF با C# 7.3 کامپایل می‌شوند؛ این جایگزین بیلد کامل net48/Costura نیست.
- `python tools/validate-ui-handoff.py`: بررسی XAML و قراردادهای layout.

QA لازم روی خروجی ویندوز: Chrome انتخاب‌شده و Firefox انتخاب‌نشده با IP متفاوت و سپس جابه‌جایی انتخاب؛ Discord/Telegram و UDP؛ Smart/Hysteria2/VLESS؛ IPv4/IPv6؛ DNS؛ اتصال مجدد؛ خاموش‌کردن split؛ اشتراک‌گذاری پراکسی و هات‌اسپات؛ تازه‌سازی بعد از نصب/حذف/آپدیت برنامه؛ خواندن Start Menu در ویندوز فارسی و مسیرهای دارای فاصله.
